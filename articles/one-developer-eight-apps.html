One developer, eight apps: the rules that keep AI-built software under control

29 November 2026 · How I build with AI · 5 min read

I'm a developer at a real-estate company in Dubai. Between Claude Code and me, we look after eight apps:

  • the lead dashboard
  • a calling app for the sales team
  • a lead router
  • an HR and admin portal
  • landing pages
  • a booking app for content creators
  • the company website
  • a CRM rebuild that's on the way

In the last 26 days I sent Claude Code 1,307 prompts. They turned into more than 450 merged pull requests and 288 finished tasks.

Those numbers aren't the point. The point is that it isn't chaos, most days. Writing code fast with AI is easy. Code you can still trust in month six is not. These are the rules that made the difference for me.

1. The project remembers, so I don't have to

Every app has a memory file, CLAUDE.md, that Claude reads at the start of every session. The dashboard's file is now over 800 lines. It covers how dates are written, which roles see which pages, what is never touched, how tests are named and what "done" means.

When I explain something twice, it goes into the file. When Claude gets something wrong because it didn't know a rule, the rule goes into the file. Over time, the file becomes the senior engineer who's been there since day one.

2. Every odd piece of data gets an ID

Real lead data is messy:

  • the same person under three phone numbers
  • a form with no project on it
  • a phone number that lost its country code on the way in
  • a reply that arrives seconds before the message it answers

Each time we fix one of these, it gets four things:

  1. an ID, like IMP-123
  2. a short entry in a registry: what happened, the rule we added, the edge cases
  3. a comment with that ID at the exact line of code
  4. a test named after it

There are about 300 of them now.

Months later, "why does the code do this?" has an answer in seconds. That goes for me, and for the AI, which reads the same registry before it changes anything.

3. A picture before any code

Every new screen starts as a static HTML mock-up. I mark it up, we change it, I approve it, and only then does it get built. Moving a chart in a mock-up costs a minute. Moving it in code costs a release.

One rule came out of this: if a page needs a paragraph to explain itself, the page is wrong. Short tooltips only.

4. Small changes, one at a time

One pull request per change. A big feature becomes a stack of small pull requests, merged in order. Each one can be read in a few minutes and undone in one click. When something breaks on live, I know which change to look at.

5. The tests are the gate

There's no CI server. Instead, the full suite runs before every merge, every time; on the dashboard that's over 1,000 tests. A merge to main goes straight to production with zero downtime, so that test run is the last thing between a change and the sales team.

Every bug fix comes with the test that would have caught it. That's how the same bug doesn't come back three weeks later in a different shape.

6. Live data is read-only while we investigate

Much of my day is questions like:

  • "Why didn't this agent get leads today?"
  • "Where did this lead go?"

Claude can look at production to answer them. Those lookups run inside a transaction that is rolled back, with phone numbers masked in the output. Secrets are never printed, not even their first few characters: a check reports pass or fail, nothing else.

Fixing live data is a separate step that I decide on and approve.

7. Never trust a silent success

When you send data to another system, "200 OK" only means it heard you. Our CRM once accepted every lead we sent and quietly dropped the phone number, because it expected it in a different shape.

So after every write to another system, we read the record back and compare.

8. Keep track of the work, not just the code

The hardest part of looking after eight apps isn't writing code. It's the interruptions. A message from sales, a broken form, a question from a manager, and the thing I was doing an hour ago is gone.

So I built a small tracker. Every evening, a script reads the day's Claude Code chats and GitHub activity, and one AI run turns them into tasks with a status, a priority and a next step, in my notes app. It's how I know the 288. I'll write about it properly in the newsletter.

Who does what

Claude writes most of the code. It digs through logs and data, drafts plans and mock-ups, and runs the tests.

I decide what we build and why, what "done" means, which design is right and what goes live. I read every plan and I merge every pull request. When the AI is confidently wrong, and sometimes it is, that's where it gets caught.

What still goes wrong

  • It works in every test and fails on live, because the server is missing a setting that the tests never needed.
  • The AI solves the problem you described, not the one you have. A vague prompt gets a confident, wrong answer.
  • I build too much. I once spent a day making a landing-page builder simpler. Three days later I replaced it with a plain upload: designers send a finished page, and it goes live. The simple version was better.
  • Long sessions lose the thread. The memory file and the registry are what bring a fresh session back up to speed.

If you're starting out

If you're a developer looking after more apps than you'd like, or a marketer who has started building your own tools with AI, begin with two things: a memory file and a test gate. Everything else on this list grew out of those two.
